# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Campbell Moda Fitness — a static storefront for a fitness-apparel brand, plus two admin-only tools. No build step, no package manager, no framework: plain HTML/CSS/vanilla JS served as-is. **100% Supabase** (Postgres + Auth + Storage + Realtime) — Firebase was fully removed from the project (see "Firebase removal" below); `supabaseClient.js` exports the one shared `supabase` client, loaded via a native browser **import map** since there's no bundler (see "Loading `@supabase/supabase-js`" below).

- `index.html` + `style.css` + `script.js` — the public storefront (product grid, product modal, cart, WhatsApp checkout, Google/email login, order history, "Meus Dados" profile/address).
- `admin.html` — admin tool (Supabase Auth-gated, email/password) to create/deactivate/delete products directly in Supabase (`produtos`/`variacoes_produto` tables, images uploaded to Supabase Storage). Not linked from the public site; reachable only from the admin menu shown to the owner's account.
- `painel-pedidos.html` — Kanban board (Novo/Confirmado/Preparando/Pronto/Entregue/Cancelado) reading/writing Supabase `pedidos`/`itens_pedido`/`historico_status_pedido` tables, live via Supabase Realtime (`postgres_changes`), with drag-and-drop (SortableJS) to move/reorder cards. Admin-only, opened from the same hidden menu as `admin.html`. Its own dark visual theme (`--bg-primary`/`--bg-secondary`/`--bg-tertiary` etc., pure Inter) is a deliberate one-page departure from the rest of the site's brand palette/Montserrat+Inter split — see below.

There are no tests, linter, bundler, or CI in this repo — it's deployed as static files (e.g. directly to a static host / GitHub Pages) and developed by opening the HTML files in a browser or via a local static server.

**Firebase removal (complete).** The project ran a Firebase→Supabase migration in stages (products+Storage, then auth, then orders+Realtime, then user profiles) before Firebase was removed entirely — no `firebasejs` CDN imports, no `firebaseConfig`, no `window.db`/`window.doc`/`window.setDoc`/`getDoc` anywhere. If you ever see any of those reappear in a diff, that's regressing to a removed dependency, not a valid pattern to extend.

**Customer profile (`perfis` table) — separate from `pedidos`, intentionally.** One row per authenticated user (`user_id` PK referencing `auth.users`, columns in Portuguese: `nome`, `email`, `telefone`, `cep`, `rua`, `numero`, `complemento`, `bairro`, `cidade`, `uf`, `foto_url`), used only to auto-fill the cart's shipping form on next purchase (`window.userProfile`, populated in `index.html`'s `handleAuthChange` and written by `window.saveUserProfile()`/`window.onProfilePhotoSelected()` in `script.js`). RLS is owner-only (`user_id = auth.uid()`, both read and write) — no admin bypass, because `pedidos.cliente_nome`/`cliente_telefone`/`cliente_endereco` already store their own snapshot at order time, so the admin never needs to read a customer's live profile to fulfill an order. Writes use `.upsert(..., { onConflict: 'user_id' })` since a user may not have a row yet on first save; because Postgres upsert only touches the columns present in the payload (same semantics as Firestore's old `{merge: true}`), a photo-only upsert never clobbers previously-saved address fields. The avatar photo goes to a separate `avatares` Storage bucket (public read, write restricted to the user's own folder via `(storage.foldername(name))[1] = auth.uid()::text` — the standard Supabase per-user-folder RLS pattern), at a **fixed path per user** (`{user_id}/avatar.jpg`, `upsert: true`) so re-uploading always overwrites rather than accumulating orphaned files; the client appends a `?v=<timestamp>` cache-buster to the public URL since the underlying path never changes.

**"Meus Dados" (`#modal-profile`)'s Nome field is editable, and `perfis.nome` — once saved — takes priority over the Google account name everywhere a name is shown.** The precedence (`window.userProfile?.name || user.user_metadata?.full_name || user.user_metadata?.name || ...`) is applied independently at every place a display name is derived: `index.html`'s `handleAuthChange` (header button label + `#client-name` cart prefill — this function's `perfis` fetch was reordered so the DB row is read *before* those two are set, otherwise there's nothing to prioritize yet), `script.js`'s `openProfileModal()` (the field's own initial value) and `onProfilePhotoSelected()`'s upsert (a photo-only save must not clobber a previously-saved custom name by re-writing it back to the Google name — this was a real bug fixed here, not hypothetical: the upsert always included `nome` before, so every avatar change silently reset any custom name). `saveUserProfile()` now reads the name from the input itself (previously it silently ignored whatever was typed and re-saved the Google name every time, since the field was `disabled` and never wired to be read) and requires it non-empty; on success it also pushes the new name into the header button and `#client-name` immediately, since neither refreshes on its own outside an auth-state-change event.

**`#profile-phone` has a live input mask and format validation, both in `script.js`.** `mascararTelefone(valor)` strips non-digits, caps at 11, and progressively formats to `(XX) XXXXX-XXXX` — wired via an `input` listener that also clears any prior `#profile-phone-error` text as the user retypes. `telefoneValido(valor)` requires the full pattern `(XX) 9XXXX-XXXX` (11 digits, mobile's mandatory leading "9") **and** that the DDD is in `DDDS_VALIDOS`, a hardcoded set of the ~67 area codes Anatel actually assigns (rejects e.g. "00" or "20", which pass a naive digit-count check but aren't real DDDs). `saveUserProfile()` blocks the save and shows the error in `#profile-phone-error` when the field is non-empty but invalid; an empty phone is still allowed (phone was never mandatory before this feature and nothing here makes it so). Because phone numbers saved before this mask existed are plain digit strings, `openProfileModal()` runs the stored value through `mascararTelefone()` before displaying it — skipping that would make re-saving an untouched legacy profile fail validation for a value the user never actually edited.

**"Meus Dados" hides its scrollbar the same way `painel-pedidos.html` does, but scoped to that one modal.** `#modal-profile .info-modal-content { scrollbar-width: none; -ms-overflow-style: none; }` plus the matching `::-webkit-scrollbar { display: none }`, in `style.css` — deliberately not applied to the shared `.info-modal-content` rule itself, since that class is reused by every info modal (About, Terms, Meus Pedidos, etc.) and only "Meus Dados" was asked for. Scrolling itself is unaffected (`overflow-y: auto` on `.info-modal-content` still applies) — only the visible bar is suppressed.

**Client-side field names differ from the database's on purpose.** `window.userProfile` and the `profile-*`/`client-*` form fields use the original English-ish names (`street`, `number`, `comp`, `neighborhood`, `city`, `photoURL`, etc.) that predate the Supabase migration; the `perfis` table uses Portuguese names per this project's DB naming convention (`rua`, `numero`, `complemento`, `bairro`, `cidade`, `foto_url`). The translation happens inline at the two Supabase call sites (`handleAuthChange`'s read, `saveUserProfile`'s write) rather than through a shared helper, since `index.html`'s module script and `script.js` are separate script contexts — don't try to factor this into one shared function without also solving how both sides would load it.

**Loading `@supabase/supabase-js`.** Resolved via a native browser **import map** (`<script type="importmap">`, one copy per HTML entry point — `index.html`, `admin.html`, `painel-pedidos.html`) pointing at a pinned jsDelivr `+esm` bundle. Do **not** point it at `esm.sh` for this package: at the pinned version, esm.sh's re-exported sub-packages (`@supabase/functions-js`, `postgrest-js`, `realtime-js`) 404, breaking the import — verified by testing in-browser; jsDelivr's `+esm` build (single bundled file, no chained sub-imports) works. When bumping the pinned version, re-test the import in a real browser before committing, not just `curl -I` the URL.

**Authentication is Supabase Auth** (`supabase.auth.*`) in all three HTML entry points. Key points for anyone touching auth code here:
- **Google login**: `supabase.auth.signInWithOAuth({ provider: 'google', options: { redirectTo: ... } })` in `script.js`'s `window.fazerLogin`. This is a full-page redirect (browser navigates away to Google and back) — there's no synchronous "login succeeded" moment to hang a toast off of; the header UI updates via the `onAuthStateChange` subscription firing after the redirect completes.
- **Apple login**: intentionally left commented out (`window.fazerLoginApple` in `script.js`, plus the button in `index.html`'s `#modal-login`) — the owner hasn't configured the `apple` provider yet in Supabase Dashboard / Apple Developer. Uncomment both when ready.
- **Email/password**: `supabase.auth.signUp(...)` / `supabase.auth.signInWithPassword(...)`. `admin.html` and `painel-pedidos.html` each have a minimal signup toggle (mirroring `index.html`'s) purely so the admin account can be bootstrapped — there's no seed/invite flow.
- **`user` object shape**: `user.id` (the auth UUID, used as `pedidos.user_id` and everywhere else an owner/identity check is needed), `user.user_metadata.full_name` (Google sign-ins may populate `.name` instead — check both), `user.user_metadata.avatar_url` (Google may use `.picture` instead — check both).
- **Email confirmation is ON for this Supabase project** (confirmed empirically — `signUp` returns `data.session === null` until the user clicks the confirmation email). All three signup flows check for this and show "verifique seu e-mail" instead of assuming an instant session.
- Google OAuth's redirect must be an allow-listed URL in Supabase Dashboard → Authentication → URL Configuration (and the Google provider itself must be enabled there with a Google Cloud OAuth client) — this is project config, not code; verified working against the real project.

## Running locally

No install step needed. Serve the directory statically so `fetch`/ES module imports work (opening `index.html` via `file://` will break the CEP lookup fetch and the module imports):

```bash
python3 -m http.server 8080   # or: npx serve .
```

Then open `http://localhost:8080/index.html`, `admin.html`, or `painel-pedidos.html` directly.

## Architecture and data flow

**`produtos.descricao` vs `produtos.composicao_especificacoes` — two different kinds of product text, not a redundant pair.** `descricao` is the short marketing blurb (always was); `composicao_especificacoes` (added later, nullable `text`, no default — same "no DB-side fallback" convention as `descricao`, the client supplies its own placeholder like `"Sem descrição."` if empty) holds the per-product technical facts that don't fit marketing copy: fabric, elasticity, warranty, whether it has a padded bra insert, etc. Neither field is client-computed from the other — if you're adding admin.html form fields for these, they're two independent textareas, not one field with a fallback to the other.

**`configuracoes_loja` is a generic key/value table for store-wide editable text, not tied to any one product.** `chave text primary key, valor text, atualizado_em timestamptz default now()` — RLS is the same public-read/admin-write shape as everywhere else (`using (true)` for `select`, `using (is_admin()) with check (is_admin())` for a single `for all` policy covering insert/update/delete; the public `select` policy already covers reads on its own, the `for all` policy's own select branch is redundant but harmless). Currently holds one row, `chave = 'cuidados_lavagem'` (care/washing instructions shown to customers) — add more rows for other editable institutional text rather than new columns or a new table per text block, that's the whole point of this table's shape. Read by `script.js`'s `loadConfiguracoesLoja()` (called once in `initStore()` alongside `loadProducts()`, cached in the module-level `cuidadosLavagem` string — it's shared across every product, so there's no reason to refetch per modal open) and written by `admin.html`'s "Configurações da Loja" card (`#config-cuidados` textarea, `window.salvarCuidadosLavagem(btn)` — takes the clicked button as a parameter rather than reading a `.btn-add` class selector, since that class is shared with "Salvar Produto" and a bare `document.querySelector('.btn-add')` would grab the wrong one).

**`produtos.composicao_especificacoes` has its own admin.html field now** (`#composicao`, labeled "Composição e Especificações", separate textarea from `#desc`/"Descrição Curta") — `addProduct()` inserts it as `composicao || null`, matching `descricao`'s own no-DB-default convention.

**The product modal (`index.html`'s `#product-modal`) has a three-tab info section** (`.product-tabs`, below the cart/buy buttons in `.modal-details`) — Descrição (`descricao`), Detalhes Técnicos (`composicao_especificacoes`), Cuidados (the shared `cuidadosLavagem` from `configuracoes_loja`). This replaced the old standalone `<p id="modal-desc">` that sat right under the price — description now lives only inside the "Descrição" tab panel (same `#modal-desc` id, just relocated into `#tab-panel-descricao`), not duplicated in both places. `window.switchProductTab(tab)` toggles `.active` on the matching `.product-tab` button and `.product-tab-panel` (`id="tab-panel-" + tab`) — pure CSS `display` swap, no re-render, no page reload. `openModal()` always calls `switchProductTab('descricao')` when opening a product, so a previously-selected tab from another product never carries over. The tab bar (`.product-tabs-bar`) is `display:flex` with no `flex-wrap` and `overflow-x:auto` (scrollbar hidden, same technique as `painel-pedidos.html`) — this is unconditional, not a mobile-only media query, so tabs never stack at any width, only scroll horizontally if they don't fit (verified by forcing the bar's width down to 180px against ~420px of actual tab content: all three tabs stayed on one row). Colors reuse the existing site tokens (`var(--primary)` for the active tab's text/underline, `var(--text-gray)`/`var(--text-white)` for inactive/hover, `var(--font-main)` for the tab labels) rather than the literal `#121212`/`#FF005C` hex the request named — `#FF005C` already *is* `var(--primary)` exactly, and `#121212` doesn't match any existing token (`--dark-bg` is `#0E0E11`, `--card-bg` is `#1B1B20`), so it read as an approximate recollection of the palette rather than a request for a new one-off color; nothing in this section needed a background fill of its own since `.modal-details`' existing background already shows through.

**Product catalog lives in Supabase (Postgres), not hardcoded.** `produtos` (one row per product: `nome`, `categoria`, `preco`, `descricao`, `composicao_especificacoes`, `imagens` — array of Supabase Storage public URLs, `ativo`) and `variacoes_produto` (one row per size: `produto_id` FK, `tamanho`, `estoque`) are normalized tables — see the schema/RLS design discussion in git history or ask for a re-summary if needed. `script.js`'s `loadProducts()` queries `produtos` with an embedded `variacoes_produto(tamanho, estoque)` select, filtered `.eq('ativo', true)` server-side. `product.id` is the Postgres `uuid` (still a string client-side, same as when it was a Firestore doc ID — every inline `onclick="...(${p.id})"` template still quotes it as `'${p.id}'`). `admin.html` writes/updates/deletes directly against these tables via the Supabase client — there is no RPC involved for product writes (unlike `criar_pedido` for checkout), just plain `.insert()`/`.update()`/`.delete()`, since this is an authenticated-admin-only flow, not a public/guest one.

**Product images use Supabase Storage, not external links.** Product images used to be external links the admin pasted in (Postimages-style) specifically because *Firebase* Storage requires the paid Blaze plan just to provision a bucket; Supabase Storage's Free plan includes 1GB storage with no card required, so the original "don't pay, don't add a card" constraint still holds even with real file uploads. The bucket is named `produtos` (public read, admin-only write — see `storage.objects` policies below), created via SQL (`insert into storage.buckets ...`), not through code, since bucket creation needs elevated privileges the app's anon/authenticated roles don't have. `admin.html`'s product form now has a real `<input type="file" multiple>` (images or short `.mp4`/`.webm`) instead of a paste-a-link textarea; each file uploads to a per-submission-random-UUID folder inside the bucket, and the resulting public URLs are what gets stored in `produtos.imagens`. Deleting a product also removes its files from Storage (path is derived by stripping the known public-URL prefix — there's no separate "storage path" column).

**Supabase Storage RLS is a separate policy set from the table RLS**, scoped to `storage.objects` with a `bucket_id = 'produtos'` condition (public `SELECT`, admin-only `INSERT`/`UPDATE`/`DELETE` via the same `is_admin()` function used everywhere else) — don't confuse this with the `produtos`/`variacoes_produto` table policies; both exist and both matter for the upload feature to work.

**Orders live in Supabase.** `pedidos` (+ `itens_pedido`, `historico_status_pedido`) are normalized tables — same shape covered in the schema/RLS discussion referenced above. `checkoutWhatsApp()` in `script.js` **never** `.insert()`s into `pedidos`/`itens_pedido` directly — RLS has no insert policy on those tables at all, by design, specifically to force every order through `supabase.rpc('criar_pedido', {...})` (a `security definer` function that validates structure and writes both tables in one transaction). If you ever see a direct `.insert()` into `pedidos` or `itens_pedido` in a diff, that's a bug being reintroduced, not a valid alternative. The "Meus Pedidos" modal (`openMyOrders()`) and `painel-pedidos.html`'s Kanban both just `.select()` normally — RLS (`user_id = auth.uid() or is_admin()` for `pedidos`, admin-only for `historico_status_pedido`) does the access control, no special-casing needed in the query itself.

**`painel-pedidos.html` uses Supabase Realtime for live updates.** `supabase.channel('pedidos-realtime').on('postgres_changes', { event: '*', schema: 'public', table: 'pedidos' }, ...)` replaces the old snapshot listener. Two things this depends on that aren't visible in the code: (1) the `pedidos` table must be added to the `supabase_realtime` publication (`alter publication supabase_realtime add table pedidos;` — a one-time SQL step, not something `ENABLE ROW LEVEL SECURITY` or the table policies do for you); (2) Realtime enforces the same RLS as normal queries, using the subscribing client's session — so a non-admin session receives no `pedidos` change events at all, same as a direct `.select()` would return nothing for them. Because a `postgres_changes` payload only carries the changed row from the one table being watched (not the joined `itens_pedido`/`historico_status_pedido`), the handler re-fetches the full pedido (`*, itens_pedido(*), historico_status_pedido(*)`) on every event rather than trying to assemble it from the payload alone — simpler and avoids partial-data bugs, at the cost of one extra round trip per change. `window.apagar()` doesn't call `renderizarPedidos()` itself — it just writes, and the realtime subscription is what triggers the re-render, for both the acting session and any other open tab.

**`painel-pedidos.html`'s Kanban is drag-and-drop (SortableJS 1.15.7, CDN, global `Sortable`), not just click-to-move.** One `Sortable` instance per `.column-cards` container, all sharing `group: 'kanban'` (lets a card move between columns) and `handle: '.card-drag-handle'` (only that grip icon starts a drag — clicking anywhere else on the card still opens `openOrderDetails()`, no conflict). Two things to know before touching this:
- **Drag targets are restricted to the same transitions the quick-action buttons already allow** (`onMove` checks `ACOES[origem]` and rejects anything else) — dragging a card straight from "Novo" to "Entregue" is blocked on purpose, because skipping "Confirmado" would skip the stock decrement in `mover_pedido_status` entirely. Don't relax this without also reconsidering the stock-skip risk.
- **Reordering within a column is real, persisted state**, not just visual: `pedidos.ordem` (`numeric`, fractional/"Trello-style" positioning — reordering between two cards just averages their `ordem`, no renumbering the whole column) drives the sort (`carregarTodosPedidos()` orders by `ordem desc`, not `criado_em` anymore). New pedidos get `ordem` from a column `default` (`extract(epoch from now()) * 1000`) — `criar_pedido()` didn't need to change at all. `calcularNovaOrdem(acima, abaixo)` handles the top/bottom/middle/empty-column cases; see it in the module script if extending this.
- Cross-column drops call the same `window.mover(id, status)` as the buttons (now returns `true`/`false` instead of nothing, so the drag handler knows whether to force a `renderizarPedidos()` to snap the card back when the RPC rejects it — e.g. insufficient stock). Same-column reorders just `.update({ordem}).eq('id', id)` directly — no RPC needed there, it's not concurrency-sensitive the way stock is.
- **Automated drag-gesture testing doesn't work here** — synthetic `MouseEvent`/`PointerEvent` sequences dispatched via JS don't reliably trigger SortableJS's internal drag state machine (confirmed while building this: same `onMove`/`onEnd` logic verified correct via direct function calls instead). A real mouse/touch drag works fine; don't read a failed synthetic-event test as a code bug without checking that distinction first.
- Empty columns render a dashed `.empty-placeholder` ("Solte itens aqui") instead of an empty `.column-cards` — `renderizarPedidos()` checks `lista.length === 0` per column before deciding what to render there.
- `.kanban-board` is centered with `justify-content: safe center`, not plain `center`. This is deliberate: with plain `center`, once the columns overflow and the board needs to scroll horizontally, the first column gets clipped off-screen to the left with no way to scroll back to it. `safe` falls back to start-alignment only in that overflow case, so the board is centered when it fits and never clips when it doesn't — verified by forcing `clientWidth < scrollWidth` and confirming the "Novo" column still renders fully at the left edge. Horizontal scrolling on `.kanban-board` (and `.column-cards`, `.modal-box`) stays scrollbar-less via `scrollbar-width: none` / `-ms-overflow-style: none` / `::-webkit-scrollbar { display: none }` — scroll still works (`scrollLeft` is settable, mouse-wheel/trackpad/drag all still scroll), only the visual bar is suppressed.

**Stock control (`variacoes_produto.estoque`) is decremented/restored atomically via `mover_pedido_status`, not client-side.** `window.mover(id, status)` in `painel-pedidos.html` calls `supabase.rpc('mover_pedido_status', { p_pedido_id, p_novo_status })` for **every** status transition (not just the ones touching stock) — this replaced the old direct `.update()` + `.insert()` pair entirely, so status change, `historico_status_pedido` insert, and any stock adjustment all happen in one transaction. The function itself, not RLS, is the authorization boundary: it checks `is_admin()` internally and raises if the caller isn't admin (same `security definer` pattern as `criar_pedido`, but `grant execute` is `to authenticated` only — never `anon`, since moving order status was never a public action). Behavior:
- Moving **to `Confirmado`** (only from `Novo`, and only if `pedidos.estoque_baixado` is still `false`): for each `itens_pedido` row, `update variacoes_produto set estoque = estoque - quantidade where produto_id = ... and tamanho = ... and estoque >= quantidade` — the `estoque >= quantidade` guard is what makes this safe under concurrency (two pedidos confirming at once can't both succeed against insufficient shared stock; the losing one's `UPDATE` matches zero rows). Zero rows affected → `raise exception` ("Estoque insuficiente..."), which aborts the *whole* transaction — no partial decrement across a multi-item order. Then sets `estoque_baixado = true`.
- Moving **to `Cancelado`** (only if `estoque_baixado` is `true`): restores every item's stock (`estoque = estoque + quantidade`), then flips `estoque_baixado` back to `false`. Cancelling from `Novo` (never confirmed) is a no-op on stock, correctly.
- Any other transition (`Preparando`/`Pronto`/`Entregue`): just status + histórico, no stock logic — but still goes through the same RPC, for the same atomicity and admin-check guarantee.
- `pedidos.estoque_baixado` (boolean, default `false`) is the single source of truth for "was stock already taken for this order" — don't infer it from `status` client-side, the column exists specifically so the function doesn't have to guess.
- Items with `produto_id is null` (product was deleted after the order was placed) or whose `(produto_id, tamanho)` no longer exists in `variacoes_produto` are silently skipped in both directions — there's nothing to decrement/restore, and that shouldn't block confirming or cancelling an otherwise-valid order.
- The pedido row is locked (`select ... for update`) before any of this, so the same pedido can't be moved twice concurrently (e.g., two admin tabs double-clicking) and double-decrement/double-restore.

**`is_admin()` never returns `NULL` — this was a real, exploitable bug, found by testing the anon path directly, not by review.** The very first version of `mover_pedido_status` checked `if not is_admin() then raise exception ... end if;`, and `is_admin()` returns `NULL` (not `false`) whenever there's no email on the session — exactly the anon case. `NOT NULL` is `NULL`, and `IF NULL THEN` in PL/pgSQL **does not run the branch** (NULL isn't true), so the exception silently never fired and an unauthenticated caller sailed straight through to the rest of the function. This never affected any RLS policy (`using (is_admin())` already treats `NULL` as "deny", same as `false`) — it only bites when `is_admin()`'s result is used as a plain boolean in *procedural* code (an `IF` inside a function body). Fixed two ways, both load-bearing: `is_admin()` itself now does `coalesce(..., false)` so it can never return `NULL` again for *any* future caller; and `mover_pedido_status` additionally checks `is_admin() is distinct from true` (safe under `NULL` regardless). **Any new `security definer` function that gates on admin status inside an `IF` must use one of these two patterns — never bare `if not is_admin()`.**

**Out-of-stock sizes are disabled in the storefront, not hidden.** `script.js`'s `loadProducts()` keeps each product's `variacoes` as `{tamanho, estoque}` pairs (not just a flat `sizes` list). `openModal()` renders a `<button disabled>` with an `.esgotado` class + "Esgotado" label for any size at `estoque === 0` — the native `disabled` attribute is what actually blocks selection (no separate JS guard needed), and CSS (`.size-btn.esgotado` in `style.css`) handles the greyed/struck-through look.

**`admin.html` has a live stock panel** (full-width card below the two main ones): a green/red dot per product in the existing list (green = at least one size with `estoque > 0`; needs `loadProducts()` there to embed `variacoes_produto(tamanho, estoque)`, not just `select('*')`), plus a separate "Estoque Baixo" list of every `(produto, tamanho)` pair at `estoque <= 2` (0 included), sorted ascending, refreshed on every `loadProducts()` call alongside the main list.

**`admin.html`'s login screen (`.login-screen`/`.login-box`/etc.) uses the same dark Lumina tokens as `painel-pedidos.html`'s login screen** (`--bg-primary`/`--bg-secondary`/`--bg-tertiary`/`--text-primary`/`--text-secondary`/`--border-primary`/`--border-hover`/`--radius-lg`, added to `admin.html`'s `:root` additively for this purpose), so the two admin tools present one consistent login experience instead of two different ones. This is scoped to the login screen only — the rest of `admin.html` (product form, product list, stock panel, `.logout-btn`) still uses the original brand tokens (`--card-bg`/`--surface-alt`/etc.) and was deliberately left alone. If either login screen's markup/CSS changes, keep the other in sync manually (same caveat as the token duplication noted below).

**`supabase/functions/importar-produto` is an Edge Function that extracts product data from raw text via the Anthropic API.** Given `{ texto: string }` (raw text an admin pastes from a supplier's page), it prompts `claude-sonnet-5` (via `ANTHROPIC_API_KEY`, a function secret — set with `supabase secrets set`, never exposed to the client) to return only a JSON object (`nome`, `descricao`, `precoFornecedor: number`, `tamanhosDisponiveis: string[]`), strips a possible ```` ```json ```` fence, `JSON.parse`s it, and validates the shape before returning it — a 422 with the raw AI response if parsing or shape validation fails, distinct from a 502 for an Anthropic API-level error. **`temperature` is not accepted for `claude-sonnet-5`** — passing it (even `0`) fails the whole request with `invalid_request_error`; don't add it back without checking the model's current param support first. JWT verification is on (the CLI/dashboard default — no `[functions.importar-produto]` override in `config.toml`), so callers need a valid `Authorization` header (anon key is enough, since this doesn't touch RLS-protected data itself); deploy via `supabase functions deploy importar-produto --use-api` (`--use-api` avoids requiring Docker locally, which isn't installed in this environment). The response also carries `confianca: "baixa" | "alta"`, the model's own judgment of whether the pasted text actually looks like a real supplier product description (concrete signals: piece name, fabric, sizes, price) versus vague/generic/unrelated text (lorem ipsum, random text, a phrase with no product info) — this exists because the function never refuses to answer: given nonsense input it still returns a full, syntactically-valid product object (tested live — vague text got `precoFornecedor: 0` and inferred sizes; pure gibberish got an honest `"nome": "Produto não identificado"` once the prompt started asking it to self-assess, versus fabricating a plausible-sounding fake product before that field existed), so `confianca` is the only signal that distinguishes a real extraction from a best-effort guess. `admin.html` uses it to show a warning, not to block anything — see below.

**`admin.html` has an "Importar do Fornecedor" section (full-width card, above the "Novo Produto"/"Produtos Cadastrados" pair) that pre-fills the product form via `importar-produto`.** The admin pastes raw supplier-page text into `#import-texto`, sets `#import-margem` (a multiplier, persisted to `localStorage['campbell_margem_multiplicacao']` on every `input` event so it isn't re-typed per import), and clicks "Processar com IA" (`window.processarImportacao()`), which calls `window.supabase.functions.invoke('importar-produto', { body: { texto } })` — the Supabase JS client attaches the session's `Authorization` header automatically, satisfying the function's JWT check. On success it fills `#name`/`#desc` directly, sets `#price` to `precoFornecedor * margem` (`.toFixed(2)`), and checks the matching `.size-stock-row` checkboxes (via `normalizarTamanho()`, which maps whatever size strings the AI returns onto the form's fixed P/M/G/GG/U set — anything that doesn't map is silently dropped, since the form has no way to represent an arbitrary size) with each stock input **set to `0`**, not auto-filled — real stock is a manual decision. `#category` is explicitly left blank (`value = ''`, matching the placeholder `<option value="" selected disabled>` added to the select) so nothing pre-picks it; `addProduct()`'s required-fields check now includes `!category`, so saving is blocked until the admin picks one — this was a deliberate gap to close, since a blank `<option>` alone doesn't stop a silent empty-string `categoria` from being inserted. **Nothing is written to Supabase by this flow** — it only populates the existing form fields; the actual insert still goes through the unchanged `addProduct()` → "Salvar Produto" path once the admin reviews/edits and submits manually. A `FunctionsHttpError`'s `.context` (a `Response`) is read for the function's own `{ error: "..." }` body so the status message shown to the admin is the specific reason (bad input, Anthropic error, JSON-parse failure), not a generic network error. When the response has `confianca: "baixa"`, a yellow `#import-confianca-baixa` banner (`.alert-warning`) is shown above the form fields ("Revise com atenção — o texto colado pode não ser uma descrição de produto válida") — this is advisory only, it doesn't disable any field or block `addProduct()`; it's reset to hidden at the start of every `processarImportacao()` call (so a second, high-confidence import clears a stale warning) and after a successful save.

**A second, independent import path sits right next to it: "Colar JSON do Fornecedor (Dalu)"** (`#import-json-texto`, `window.processarJsonFornecedor(btn)`) — for a specific supplier (Dalu) that hands over structured JSON (`{ nome, preco, descricaoSimples, descricaoCompleta, tamanhos: [{tamanho, disponivel}], imagens: [urls] }`) instead of raw text, so there's no AI call here at all, just `JSON.parse` plus field mapping. It reuses `#import-margem` (same multiplier, same localStorage key — the two importers share one margin, not two), `normalizarTamanho()`, `imagensImportadas`/`renderImagensImportadas()` (images go through the same array the single-URL "Baixar Imagem" field feeds, so results from both importers can coexist in one product), and the same blank-category convention as the AI path. Both "Processar com IA" and "Processar JSON" carry the class `btn-import`, so their handlers take the clicked button as a parameter (`onclick="processarJsonFornecedor(this)"`) rather than `document.querySelector('.btn-import')` — that selector would silently grab whichever of the two buttons comes first in the DOM, not necessarily the one clicked (the same class-collision issue fixed earlier for `.btn-add` when "Salvar Cuidados e Lavagem" was added next to "Salvar Produto").
- `descricaoSimples` → `#desc` directly; `preco * margem` → `#price`, same as the AI path.
- **`composicao_especificacoes` is NOT `descricaoCompleta` verbatim** — `extrairComposicaoDeDescricaoCompleta()` cuts it at the earlier of the (case-insensitive) substrings `"Instruções de lavagem"` or `"Cuidados"`, whichever appears first, and drops everything from there on. That trailing section is Dalu's own boilerplate care instructions, which duplicate the shared `configuracoes_loja` "Cuidados" text (see above) — keeping it per-product would defeat the point of that shared table. If neither marker is found, the full `descricaoCompleta` is used as-is (nothing to cut).
- Images: unlike the single-URL field's one `importar-imagem` call, this loops the `imagens` array **sequentially** (not `Promise.all`) — deliberately, to avoid hammering the edge function with N simultaneous cold-ish invocations, and because the status text needs to show progress ("Baixando imagem X/N...") meaningfully. One URL failing doesn't stop the loop or block the rest of the form — failures are collected and summarized at the end (`"N de M imagens falharam..."`), successes still land in `imagensImportadas` same as always. This was tested with a real two-image JSON payload end-to-end (including the composição cut, which correctly excluded a "Instruções de lavagem" section from a test payload) and with both an unparseable and a structurally-incomplete JSON string, confirming the rest of the form stays untouched in both error cases.

**`supabase/functions/importar-imagem` downloads a supplier image URL server-side and uploads it to the `produtos` Storage bucket, avoiding the CORS/anti-bot restrictions a client-side `fetch` of a supplier CDN would hit.** Given `{ url }`, it fetches the URL (15s timeout, spoofed browser `User-Agent` since some CDNs block non-browser clients), rejects anything whose body exceeds 8MB (same cap as the manual upload flow), then uploads the bytes to `produtos/<uuid>/importada.<ext>` and returns `{ url: publicUrl }`.

**Content-type validation has two tiers, because some supplier CDNs lie about it.** `assets.sistemawbuy.com.br` (the Dalu supplier CDN) serves real JPEGs with `content-type: application/octet-stream` — confirmed directly with `curl` against a real product image URL, not a guess — and browsers already handle this by sniffing the actual bytes instead of trusting the header, so the function does the same. An explicit non-image `content-type` (e.g. `text/html` from a pasted product-page URL instead of the image itself) is still rejected immediately, before downloading the body — no reason to pay for that download. But `content-type` that's empty or exactly `application/octet-stream` is treated as "unknown, not rejected yet": the body is downloaded (still subject to the same 8MB cap) and `detectarTipoImagemPorAssinatura()` checks the first bytes against known magic numbers (JPEG `FF D8 FF`, PNG `89 50 4E 47`, WEBP: `"WEBP"` — bytes `57 45 42 50` — at offset 8, since WEBP is a RIFF container). A signature match wins over the CDN's useless header — the *detected* type, not the original `content-type`, is what gets used for the file extension and the Storage `contentType` on upload (this is why the Dalu example above lands in Storage correctly `Content-Type: image/jpeg`, verified after upload, not `application/octet-stream`). No match on either front (neither an `image/*` header nor a recognized signature) is still a hard rejection, with a message that names both things that were checked. **Authorization is not a custom check in the function** — it creates its Supabase client with the *caller's* `Authorization` header (not the service role key) and lets the existing `storage.objects` RLS (admin-only `INSERT` via `is_admin()`) do the gating; a non-admin caller's upload simply fails with the same RLS error everyone else gets, so this doesn't duplicate `is_admin()` logic. `SUPABASE_URL`/`SUPABASE_ANON_KEY` are read from `Deno.env` — these are auto-injected by the platform into every Edge Function, not secrets you set (don't confuse with `ANTHROPIC_API_KEY`, which is a real secret, in `importar-produto`).

**`admin.html`'s "URL da Imagem (Fornecedor)" field (`#import-imagem-url`, next to the manual file upload) calls `importar-imagem` and treats a successful result exactly like a manual upload.** `window.baixarImagemFornecedor()` invokes the function, and on success pushes the returned public URL into a module-level `imagensImportadas` array (rendered as small removable thumbnails in `#imagens-importadas-preview`) — **not** into the `#images` file input, since that input can only hold real local `File` objects. `addProduct()` was changed to build `imagens` as `[...imagensImportadas, ...imagensUpload]` (uploading `#images`' files only if any were chosen) and its required-fields check now accepts `files.length === 0 && imagensImportadas.length === 0` as the "no image" failure case instead of just `files.length === 0` — a product can be saved with only imported-by-URL images, only manually-uploaded ones, or a mix of both. A failed download shows the function's error message in `#import-imagem-status` and stops there — it never touches `imagensImportadas`, `#images`, or any other form field, so the rest of the form (including anything already imported successfully) stays intact and the admin can fall back to manual upload without re-entering anything.

**Admin visibility is a hardcoded email check**, not a database role/claim: in `index.html`'s `handleAuthChange` (subscribed via `supabase.auth.onAuthStateChange`), the admin menu (links to `painel-pedidos.html` and `admin.html`) is shown only when `user.email === 'othaviocampbell2015@gmail.com'`. Anyone who knows the URLs can still open `admin.html`/`painel-pedidos.html` directly — there's no server-side authorization at the page level (Postgres RLS is what actually protects the data), so treat the menu visibility as UI-only gating, not real access control.

**Two-script loading order matters in `index.html`:** the inline `<script type="module">` initializes the Supabase client and sets `window.supabase`/`window.userLogado` *before* dynamically appending `script.js` to the DOM. `script.js` is a plain (non-module) script and depends on `window.supabase` already existing — don't reorder this or convert `script.js` to a module without also updating how it accesses Supabase.

**No client-side router or component framework.** All UI state (cart contents, which modal is open, selected size, current product) lives in a handful of module-level variables in `script.js` (`cart`, `currentModalProduct`, `selectedSize`) and is re-rendered by directly rebuilding `innerHTML` strings. Nearly every interactive function is attached as `window.fnName = function() {...}` so it can be called from inline `onclick="..."` attributes in the HTML — this is the established pattern for adding new UI actions, not an oversight to "fix" with addEventListener refactors.

**Checkout has no payment integration.** `checkoutWhatsApp()` calls `criar_pedido` (see above), then opens a `wa.me` deep link with a pre-filled, `encodeURIComponent`-escaped message summarizing the cart and address; the actual payment/confirmation happens off-platform in a WhatsApp chat with the store.

**Checkout requires a phone number, sourced from the profile when possible.** `checkoutWhatsApp()` runs `window.userProfile?.phone` through `mascararTelefone()` and only treats it as usable if `telefoneValido()` passes on the *normalized* result — not just "is it non-empty." This matters because `perfis.telefone` can hold digits saved before the mask/validation feature existed (e.g. `"32984192045"`), and normalizing-then-validating silently upgrades those to the real format (`"(32) 98419-2045"`) instead of either breaking checkout or skipping validation for legacy accounts; `atualizarCampoTelefoneCarrinho()` does the same normalize-then-check (not a bare truthiness check) so `#client-phone-group` correctly reappears for a legacy or otherwise-invalid saved phone instead of staying hidden and letting a bad value through silently. Only when nothing valid comes out of that does `#client-phone-group` (hidden by default, toggled on every `toggleCart()` call) become the source, validated the same way, blocking checkout with an inline error if incomplete/invalid — same pattern as the existing name/address checks. After a successful `criar_pedido` with a phone that came from this fallback field (not the profile), it's also `upsert`ed into `perfis` (skipped for guests — no `user_id` to attach it to) so the field doesn't reappear on the next purchase; this is a plain client upsert (not the sync RPC below), since it's the user's *own*, first-time profile write, not propagating a change into other orders. Note this doesn't retroactively fix a legacy phone *in* `perfis` — only the value actually sent to `criar_pedido` is normalized; the profile row keeps the old raw digits until the user next saves it themselves (through "Meus Dados" or the fallback-field path above), which is fine since normalization is cheap and repeats correctly every time.

**`criar_pedido` validates phone *format* server-side too, not just non-empty — added after finding the gap by testing directly against the RPC (not a hypothetical): `cliente_telefone: "abc123"` was accepted and created a real order before this fix.** The function now requires the exact `(XX) 9XXXX-XXXX` shape (regex `^\(\d{2}\) 9\d{4}-\d{4}$`) *and* a real Anatel-assigned DDD (same whitelist as `DDDS_VALIDOS` in `script.js`, reimplemented in SQL as `= any(array[...])`, checked via `substring(cliente_telefone from 2 for 2)::int` since the format is fixed-width) — same defense-in-depth reasoning as the `is_admin()` NULL bug documented above: client-side validation alone doesn't hold for a `security definer` function anyone can call directly. **This has a real interaction with the legacy-phone-normalization note just above**: `criar_pedido` now *rejects* an unnormalized legacy phone outright, so `checkoutWhatsApp()` normalizing before calling it isn't just a nicety anymore, it's load-bearing — skipping that step would break checkout for any account with a phone saved before the mask existed. Verified with real RPC calls after deploying: `"abc123"` and a well-formatted-but-fake DDD (`"(00) 98888-7777"`) both rejected with distinct error messages, a properly formatted number still succeeds, and a full storefront checkout (not just the raw RPC) with a legacy unmasked profile phone works end-to-end post-fix.

**Editing the phone in "Meus Dados" propagates to that user's still-open orders, via `sincronizar_telefone_pedidos(p_telefone)` (`security definer`, `where user_id = auth.uid() and status not in ('Entregue','Cancelado')`).** `saveUserProfile()` calls it whenever the new phone differs from `window.userProfile.phone` prior to the save — deliberately a plain RPC call rather than a direct client `.update()` on `pedidos`, consistent with this project's rule that any mutation of `pedidos` beyond the owner's own `SELECT` goes through a narrow, purpose-built `security definer` function (the same reasoning as `criar_pedido`/`mover_pedido_status`) rather than trusting broader RLS write access, which `pedidos` doesn't grant to regular users at all. The RPC sets `pedidos.telefone_atualizado = true` alongside the new `cliente_telefone`, and this flag is what drives the Kanban indicator below — a boolean, not a timestamp, since nothing here needs to show *when* it changed, only *that* it did (and it's naturally exclusive with the original checkout value, which never sets the flag). If the sync RPC errors, the profile save still succeeds — it's `console.error`-only, non-blocking, since the phone did get saved to the profile either way.

**`painel-pedidos.html` reflects an updated phone two ways, both driven by `pedidos.telefone_atualizado`** (included automatically since `SELECT_PEDIDO_COMPLETO` is `select('*', ...)`, no query change needed): a small amber dot (`.bg-whats.tel-atualizado::after`) on the card's WhatsApp quick-action button; and, in `openOrderDetails()`'s modal, the phone number itself (`#m-phone`) plus an explicit `#m-phone-badge` pill ("Telefone atualizado") right next to it. Both update live through the existing `postgres_changes` subscription — no special-casing needed, since an `UPDATE` from the sync RPC is indistinguishable to the subscriber from any other `pedidos` change.

**The compact Kanban card itself now shows the client's full name and phone number directly** (`renderizarPedidos()` in `painel-pedidos.html`) — this was a deliberate departure from the original Lumina redesign's minimal-card philosophy (which deliberately kept the tile to first-name-only, no phone), made because the admin needed to see who/how-to-reach-them without opening the details modal for every card. `.c-nome` now holds `p.cliente_nome` in full (was `.split(' ')[0]`), and a new `.card-phone` line (WhatsApp icon + `p.cliente_telefone`, `'Telefone não informado'` if empty) sits between the title and the item-count line. The `telefone_atualizado` badge now also appears inline next to this visible phone (same `.badge-tel-atualizado` class already used in the details modal), in addition to the existing dot on the WhatsApp button — both indicators still coexist, this doesn't replace one with the other.

**WhatsApp messages sent from the Kanban are status-aware, not one generic template.** `mensagemWhatsappPorStatus(p, id)` (a `switch` on `p.status`, `painel-pedidos.html`) returns different copy per column — Novo/Confirmado/Preparando/Entregue/Cancelado each have their own, and **Pronto** additionally branches on `p.tipo_entrega` ("pronto pra retirada" vs. "sai pra entrega em breve", since those are different asks of the customer). `window.abrirWhatsapp(id)` calls this instead of building one hardcoded string inline, same `telefoneParaWhatsapp()`/`wa.me` mechanics as before. Tested by driving a real test order through every status via `window.mover()` (not synthetic fake objects) and intercepting `window.open` to capture the generated message text at each step — the one subtlety hit while testing this way: `ordersData` (and this function) live inside `painel-pedidos.html`'s module script and are **not** on `window` (same reason `window.supabase` isn't exposed there either — see below), so reaching them from outside requires driving the page's own `window.mover`/`window.abrirWhatsapp`/quick-action-button entry points, not reading module internals directly; and after `mover()` resolves, `ordersData[id].status` only updates once the Realtime `UPDATE` round-trips back (`atualizarPedidoNoPainel`), so a script that calls `abrirWhatsapp` immediately after `mover()` without waiting for that can observe the *previous* status's message — not a product bug, just a timing gotcha for anything scripting this page externally.

**CEP (Brazilian postal code) autofill** uses the public ViaCEP API (`viacep.com.br`) directly from the client in `buscarCep()`, shared between the cart's shipping form and the profile modal via a `type` ("client" | "profile") parameter that selects which set of `id="{prefix}-*"` fields to fill.

## Conventions worth matching

- Portuguese (pt-br) for all UI text, comments, and database field/table names (`produtos`, `pedidos`, `cliente_nome`, `itens_pedido`, `endereco`); keep new code consistent with this rather than mixing in English field names.
- CSS uses custom properties in `:root` — a small design system (colors, an 8px spacing scale `--space-xs` … `--space-2xl`, `--radius-sm`/`--radius-md`, and `--font-main`/`--font-body`) defined once in `style.css`; `admin.html` and `painel-pedidos.html` redeclare their own local copies of the same tokens in inline `<style>` blocks since they're standalone pages — keep all three in sync manually if any token changes. Palette: `--primary: #FF005C` (Magenta Campbell), `--accent: #CBFF3D` (Lima Energia), `--secondary: #25D366` (WhatsApp green — reserved only for WhatsApp-branded elements, not general UI), `--dark-bg`/`--card-bg`/`--surface-alt`/`--border-color`/`--text-white`/`--text-gray`. Typography: Montserrat for headings/CTAs (`--font-main`), Inter for body/forms/labels (`--font-body`). Buttons/cards use small sharp radii (4–8px), not pill shapes, by design. Breakpoints: mobile ≤599px, tablet 600–1023px, desktop 1024px+.
- Currency is formatted manually everywhere via `.toFixed(2).replace('.', ',')` rather than `Intl.NumberFormat` — follow the same pattern for consistency.
- Media items (product images/cart thumbs) can be images or short looping videos; the convention for telling them apart is a file-extension check (`.endsWith('.mp4')`/`.webm`), reused in `getMediaHTML`, `slideImage`, `changeModalMedia`, and cart rendering — extend that same check rather than adding a separate media-type field.
